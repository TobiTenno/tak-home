Setup guide

This walkthrough sets up a Docker-first CloudTAK + TAK Server stack behind SWAG, optional T.Rex maps, and Authelia + LLDAP for SSO (in a separate auth-home stack). Your checklist progress is saved in this browser. Use the Copy button on any command block to grab it for the terminal.

What you get

HostnameRole
map.<domain>CloudTAK web UI (Let’s Encrypt via SWAG)
tiles.<domain>CloudTAK tiles / Hosted PMTiles
tak.<domain>ATAK (8089 and related ports) — TAK private CA, stream passthrough
auth.<domain>Authelia login (optional admin UI at /auth-admin/)
Two certificate worlds. Map and tiles use SWAG’s Let’s Encrypt certificates. TAK client ports use the TAK private CA. Do not copy TAK *.pem / *.p12 files into SWAG’s /config/keys, and leave tak out of Let’s Encrypt SUBDOMAINS.
browser │ HTTPS 443 ▼ SWAG ── map → tak_api:5000 ├── tiles → tak_tiles:5002 ├── auth → Authelia (+ /auth-admin) └── stream 8089/8443/… → tak_server (no decrypt) Authelia ← LDAP → LLDAP │ OIDC ▼ CloudTAK (+ TAK CoreConfig oauth for cert enroll)

1 · Copy & run setup

On the server, place this project next to your shared Compose file, then run setup (the two forms below are equivalent): 

./setup.sh example.com -f ../docker-compose.yml
./setup.sh -h example.com --file ../docker-compose.yml
./setup.sh example.com -p opentopomap

The default map provider is trex; pass -p to choose another.

-f points at the root Compose file to update. Setup copies the stack into a tak-home/ directory beside that file and adds an include for tak-home/compose.yaml.

You can safely re-run setup later: it refreshes hostnames but keeps secrets already present in config/secrets.env and config/cloudtak.env.

    2 · Wire SWAG

    This stack does not publish host ports itself. Services talk on the Docker network tak; SWAG should join that network and publish the public ports: 

    services:
  swag:
    networks:
      - tak
    ports:
      - "443:443"
      - "8089:8089"
      - "8443:8443"
      - "8446:8446"
      - "9001:9001"
networks:
  tak:
    name: tak

    Install the generated nginx snippets into SWAG:

    Generated fileCopy into SWAG
    swag/cloudtak.conf/config/nginx/site-confs/
    swag/tak-stream.conf/config/nginx/stream-confs/ (not site-confs)

    In SWAG’s nginx.conf, add a top-level stream block next to http so the stream configs load: 

    stream {
    include /config/nginx/stream-confs/*.conf;
}
    docker exec swag nginx -t && docker exec swag nginx -s reload
    docker exec swag netstat -tlnp | grep -E '443|8089|8443'
    On the map vhost, location / should proxy to tak_api.tak:5000 (or tak_api on the same network). Route /pmtiles/ to tak_pmtiles, and the tiles host to tak_tiles:5002.

    If you use remote basemaps (T.Rex hillshade, Google, and similar), set NGINX_CSP_IMG_SRC and NGINX_CSP_CONNECT_SRC in config/cloudtak.env, then recreate tak_api so the headers pick up the change.

      3 · Bring up the stack

      From the directory that contains the Compose file you passed to -f:

      docker compose -f ../docker-compose.yml up -d tak_certs tak_database tak_server
      docker compose -f ../docker-compose.yml cp \
  tak_server:/opt/tak/certs/files/root-ca.pem tak-home/tak-ca.pem
      docker compose -f ../docker-compose.yml up -d \
  tak_certs tak_database tak_server tak_api tak_tiles tak_events \
  tak_retention tak_media tak_postgis tak_store tak_pmtiles
      Using --profile tak also starts every service that has no profile. Prefer listing the services you want, as above.

      Quick check that the API is reachable through SWAG (a 401 means it is up):

      curl -sk -o /dev/null -w '%{http_code}\n' https://map.example.com/api/server

        4 · Maps (T.Rex / Hosted)

        If your chosen provider ships a fetch.sh, run it on the server to pull tiles (and related assets): 

        ./maps/fetch.sh
        ./maps/fetch.sh --regions ks,mo,ar
        ./maps/fetch.sh --regions conus --elevation
        ./maps/fetch.sh --sprites-only

        Region IDs are listed in maps/providers/trex/regions.tsv. Sprites are proprietary and gitignored — keep them on the deploy host only. 

        ./maps/render-basemap.sh --hosted \
  --tiles-host tiles.example.com --features ks-mo-features
        ./maps/publish-garage.sh
        ./maps/publish-garage.sh --as ks-mo-features features.pmtiles
        Hosted tile URLs must use {$z}/{$x}/{$y} (with the dollar signs), not bare {z}. After publishing to Garage, the script restarts tak_tiles so stale ETags do not cause 412/500 errors. In CloudTAK, Garage PMTiles should use protocol hosted with type vector — not a pmtiles protocol value.

          5 · ATAK enrollment

          Once TAK Server is up, build a datapackage whose hostname matches the name on the certificate: 

          ./make-datapackage.sh tak.example.com

          Install that package in ATAK and trust the TAK private CA — not the Let’s Encrypt certificate used for the map site.

            6 · Authelia + LLDAP SSO

            Identity lives in a separate sibling project, auth-home — not inside this Compose stack. Authelia handles login, 2FA, and OIDC; LLDAP is the user directory; an optional admin UI is available at https://auth.example.com/auth-admin/. See the auth plan for the longer design notes.

            6a · auth-home setup

            cd /path/to/auth-home   # your git clone is fine
            ./setup.sh example.com -f ../docker-compose.yml
            ./setup.sh example.com -f ../docker-compose.yml --admin-expose tailscale
            ./setup.sh example.com --no-swag

            With -f, setup copies the stack next to that Compose file as auth-home/ (same idea as tak-home), adds an include for auth-home/compose.yaml, ensures the root networks auth and tak exist, and attaches the swag service to both. Use --admin-expose with subnet, localhost, tailscale, or public to control who can reach the admin UIs. --no-swag publishes host ports via compose.no-swag.yaml instead of relying on the proxy. Containers are named auth_lldap, auth_authelia, and (optionally) auth_authelia_admin. 

            docker compose --profile auth up -d
            docker compose --profile auth --profile admin up -d
            docker compose -f compose.yaml -f compose.no-swag.yaml --profile auth up -d
            cp swag/auth.conf /path/to/swag/config/nginx/site-confs/
            docker exec swag nginx -t && docker exec swag nginx -s reload

            After SWAG is proxying auth, confirm OIDC discovery:

            curl -sk https://auth.example.com/.well-known/openid-configuration | head

            Client ID and secret for CloudTAK are written to auth-home/config/secrets/cloudtak-oidc.txt.

            6b · CloudTAK Admin → Login

            FieldValue
            Enable OIDC SSOOn

            The identity provider must return an email claim. CloudTAK uses that email as the username.

            6c · TAK Server CoreConfig

            Add OAuth to CoreConfig so new SSO users can enroll a client certificate: 

            <oauth usernameClaim="email">
  <openIdDiscoveryConfiguration
    name="cloudtak-sso"
    clientId="cloudtak"
    secret="SAME_PLAINTEXT_SECRET"
    redirectUri="https://map.example.com/api/login/oidc/callback"
    configurationUri="https://auth.example.com/.well-known/openid-configuration"/>
</oauth>
            docker compose -f ../docker-compose.yml restart tak_server
            Do not put Authelia forward-auth alone in front of CloudTAK — CloudTAK needs its own OIDC session. ATAK continues to use client certificates.

            Other apps

            You can point other apps at the same auth stack by adding OIDC clients outside tak-home. Prefer native OIDC when the app has its own session model; reserve forward-auth for simpler cases.

              7 · Migrate existing users

              WhatCan you migrate it?
              Emails / usernamesYes — into LLDAP uid and mail
              Password hashesNo — LLDAP uses OPAQUE; foreign hashes will not import
              Plaintext USER_PASS_*Yes — use --migrate-plaintext-pass
              ATAK client certificatesLeave them as-is; they keep working

              From your auth-home deploy (adjust the path to tak-home if needed):

              ./scripts/migrate-users.sh --tak-home ../tak-home --email-domain example.com --dry-run

              Without plaintext secrets, the script assigns random temporary passwords (printed once):

              ./scripts/migrate-users.sh --tak-home ../tak-home --email-domain example.com

              If you still have plaintext passwords from an earlier deploy, seed them from tak-home’s config/secrets.env (USER_PASS_*) as the initial LLDAP passwords: 

              ./scripts/migrate-users.sh --tak-home ../tak-home --email-domain example.com --migrate-plaintext-pass
              ./scripts/migrate-users.sh --tak-home ../tak-home --email-domain example.com --migrate-plaintext-pass --dry-run

              Or supply a TSV (username<TAB>email[<TAB>password]):

              ./scripts/migrate-users.sh --users-file ./users.tsv --migrate-plaintext-pass
              1. Dry-run first and confirm the emails match existing CloudTAK usernames.
              2. Turn on SSO with enforce still off; matching emails reuse the existing profile.
              3. When you are ready, set oidc::enforced.
              Locked out after enabling enforce? Use an admin token to PUT /api/config with {"oidc::enforced": false}, or delete that settings row in the CloudTAK database.
